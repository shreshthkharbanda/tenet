# Deployment affinity and compatibility pre-call filters (AFFINITY)

## Purpose
This module holds the router's optional deployment filters. The router runs them after its own health, cooldown and blocked-deployment filtering and before the routing strategy picks one deployment. Each filter narrows the candidate list so that a request lands on a deployment that already holds its state, or on one that can serve it at all. The state can be a per-caller pin, a per-session pin, a Responses API `previous_response_id`, encrypted reasoning minted by one upstream account, or a provider prompt-cache prefix. "Can serve it" means a deployment that supports assistant prefill for a mid-stream continuation. The module also owns two supporting pieces. One is the prompt-cache pin store: it derives keys from the cacheable message prefix and walks back over earlier breakpoints. The other is the splice logic that joins a fallback's continuation onto a stream the client has already partly received. Every filter is advisory. When it cannot find or use a pin, it returns the candidates it was given, or it degrades. It never raises on a missing pin.

Terms used throughout:
- **Candidate list**: the `healthy_deployments` list a filter receives, made of router deployment dicts with `model_name`, `litellm_params` and `model_info.id`.
- **Pin**: a cache entry that maps a scope (a caller, a session or a prompt prefix) to a deployment id (`model_info.id`).
- **Model group**: the public `model_name` a caller asks for.
- **Encryption boundary**: the pair (`api_base`, `api_key`) that decides which upstream account can decrypt encrypted reasoning.

## Scope and boundaries
In scope: five pre-call check files under `litellm/router_utils/pre_call_checks/` and the prompt-cache pin store `litellm/router_utils/prompt_caching_cache.py`. Every in-scope file is cited by at least one claim below.

`responses_api_deployment_check.py` is live code that nothing wires in. The router maps the `responses_api_deployment_check` setting onto `DeploymentAffinityCheck`, and no library code constructs `ResponsesApiDeploymentCheck` ([AFFINITY-002]).

Out of scope, owned elsewhere:
- **router-setup** (`litellm/router.py`): registers the checks from `optional_pre_call_checks`, `model_group_affinity_config` and `enable_mid_stream_fallback_continuation` ([RSETUP-136]-[RSETUP-146], [RSETUP-060]).
- **router-selection**: runs the callback filter loop, applies `continuation_deployments` on the synchronous path, and bypasses the strategy for an encrypted-content pin ([RSELECT-047], [RSELECT-123], [RSELECT-066]).
- **router-calls**: builds continuation messages and wraps the stream in `ContinuationOutput`. On fallback hops it also calls `strip_reasoning_the_targets_cannot_decrypt` and stamps `deployment_model_name` and `model_info` into request metadata ([RCALL-008], [RCALL-014], [RCALL-080], [RCALL-068]).
- **Out-of-scope libraries**:
  - `litellm/caching/affinity_cache.py`: the atomic first-writer-wins claim.
  - `litellm/caching/dual_cache.py`: the in-memory and Redis tiers.
  - `litellm/responses/utils.py`: the codecs for response ids, `encitem_` ids and `litellm_enc:` wrapping, and the stripping of Responses input.
  - `litellm/litellm_core_utils/prompt_templates/common_utils.py`: stripping of Anthropic-shaped blocks.
  - `litellm/integrations/anthropic_cache_control_hook.py`: auto-injected cache breakpoints.
  - `litellm/utils.py`: token thresholds and model capabilities.

Inbound callers:
- router-setup, router-selection and router-calls (above).
- The complexity router (`litellm/router_strategy/complexity_router/complexity_router.py`), which calls `DeploymentAffinityCheck.get_user_key_from_request_kwargs`.
- The SDK async call wrapper and the synchronous Responses handler, which call `async_pre_call_deployment_hook` ([AFFINITY-012]).
- The logging success path, which calls `PromptCachingDeploymentCheck.async_log_success_event`.

Outbound calls: the DualCache tiers (memory and Redis), the codec helpers listed above, the cost-map capability lookups, the token counter (offloaded to worker threads) and `litellm.post_call_rules`.

## Validation rules
None of these filters validates or rejects a request. They read optional fields defensively, and a field that is malformed or absent disables the corresponding pin rather than producing an error. The exceptions are listed under Error handling.

## Implementation notes
The following notes are informative. Where a note describes something observable, it points to the normative claim.

- Hash choices are load-bearing. Caller keys use SHA-256 hex ([AFFINITY-035]). Prompt-cache keys use a SHA-256 chain over canonical JSON ([AFFINITY-106], [AFFINITY-165]). Pins live in a shared Redis, so another pod or version must derive byte-identical keys to find them. Pins are not interoperable between key schemes. The `v1` in `deployment_affinity:v1` is the only version marker.
- The prompt-cache walk-back mirrors the provider's cache lookup window. Positions count blocks, with a run of tool blocks counted as one position. The newest pin wins because a later prefix extends an earlier one.
- The pod-local claim and the Redis script implement the same first-writer-wins rule. Keeping them in agreement means the Redis path and the outage path behave identically for a single pod.
- The encrypted-content filter is cache-free by design. The deployment id travels inside opaque client-visible strings (`encitem_...` ids and `litellm_enc:` wrappers), which the response post-processor writes and the request pre-processor unwraps before forwarding. Both of those live outside this module.
- The continuation sentinel is a private object instance rather than a boolean. Request JSON cannot produce it, so a client cannot steer routing onto prefill-capable deployments.
- Two unused helpers are dead within this module: `DeploymentAffinityCheck._set_local_pin` and `DeploymentAffinityCheck._claim_pin_in_memory`. No caller in the module uses them. They mirror the shared claim helpers.

## Suspected defects
Behavior that looks unintended. The normative sections above state what the code does; each claim here says why it looks wrong and who is affected.

- [AFFINITY-198] {confirmed} `litellm/router_utils/pre_call_checks/deployment_affinity_check.py:560-589`, `litellm/caching/affinity_cache.py:58-80` A caller or session pin that names a deployment no longer among the candidates is neither cleared nor replaced, because the first-writer-wins claim keeps the stale id ([AFFINITY-162], [AFFINITY-163]). Looks unintended because affinity exists to keep a caller on one deployment, yet while the stale pin lives each request goes to an arbitrary other deployment without re-pinning. Impact: after a deployment is removed or stays unhealthy, its callers lose stickiness and prompt-cache reuse for up to the pin TTL (`3600` s by default, [AFFINITY-003]).
- [AFFINITY-199] {confirmed} `litellm/router_utils/pre_call_checks/prompt_caching_deployment_check.py:97-101`, `litellm/router_utils/pre_call_checks/prompt_caching_deployment_check.py:182-185` The prompt-cache read gate counts tokens for the requested group name, while the write gate counts for the serving deployment's model ([AFFINITY-186]). Looks unintended because both gates decide the same question, whether the prompt is long enough to cache. Impact: near the threshold, pins are written that are never read, or reads are attempted for prompts that are never pinned.
- [AFFINITY-202] {confirmed} `litellm/litellm_core_utils/logging_callback_manager.py:297-320`, `litellm/router.py:1630-1651` Under [AFFINITY-200], a router whose check instance was kept out of `litellm.callbacks` silently loses that check when the router whose instance was registered is discarded, and meanwhile every router in the process, including routers that never listed the check, reads and writes pins through the registered router's caches and resolves encryption boundaries against its deployments. Looks unintended because `Router.discard()` is documented as cleanup for a router that is no longer used, yet it disables affinity for routers still in use, and each router builds its own instance bound to its own caches and router. Impact: an SDK process that builds several routers with the same checks and discards the first loses affinity on the others, and routers that share a process share pins; in the proxy, a per-request `user_config` router (built and discarded per call, `litellm/proxy/route_llm_request.py:41-53`) that lists checks the main router already has runs the main router's instances and caches instead of its own.
- [AFFINITY-203] {confirmed} `litellm/router.py:14700-14713`, `litellm/router.py:15629-15640`, `litellm/router.py:15691-15693` On the synchronous selector ([AFFINITY-012]) none of this module's filters runs and nothing is logged, so under a router-level strategy such as `usage-based-routing` even async calls get no caller, session, `previous_response_id`, encrypted-content or prompt-cache affinity while their caller and session pins are still written. Looks unintended because the same selector refuses to run with routing plugins configured, with an error saying that silently skipping the plugin pipeline on this path would let a policy be bypassed, and affinity configured through `optional_pre_call_checks` is skipped the same way without any signal. Impact: deployments that pick a legacy strategy, or call sync Router methods, see no stickiness and no encrypted-content pinning or stripping, and their pin writes only consume cache space.
