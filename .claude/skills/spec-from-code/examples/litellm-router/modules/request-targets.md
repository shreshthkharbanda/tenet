# Request-to-target resolution helpers (TARGETS)

## Purpose
This module holds the helpers that turn a request's model name and caller into one concrete upstream
target. It does not pick the deployment; the Router's selection pipeline does that. It decides seven things:
1. How wildcard model names (`openai/*`, `*meta.llama3*`) match requests and rewrite the provider model.
2. How a deployment flagged for Kubernetes pod discovery has its `api_base` host replaced by one pod IP,
   chosen round-robin or by session affinity.
3. How caller-supplied `api_key` / `api_base` / `base_url` change the per-request deployment record (id,
   pricing, metadata), and which admin-configured fields that record drops when the caller redirects the
   base URL. The provider call itself is built from the deployment's own parameters plus the request
   kwargs, so those dropped fields still reach it ([TARGETS-211]).
4. How a deployment's `max_parallel_requests` cap is enforced. Each attempt over the cap fails fast with a
   429 instead of queueing, and the Router's retry loop may retry that 429 ([TARGETS-076]).
5. How candidate deployments are filtered by team ownership and web-search capability, and how alias maps
   resolve the model a request is served from.
6. How a batch JSONL upload has every row's `body.model` rewritten to the selected deployment's model.
7. How search-tool requests are spread across tools that share a name and sent through the Router's
   retry and fallback loop, which applies fallbacks by tool name but by default does not retry a search
   ([TARGETS-143]).

## Scope and boundaries
In scope: seven files under `litellm/router_utils/` (about 1,810 non-blank lines). All of them are listed in the frontmatter.

Out of scope and owned elsewhere:
- The Router class (`litellm/router.py`, modules `router-setup`, `router-calls`, `router-dispatch`,
  `router-deployments`, `router-selection`). It constructs the `KubernetesPodDiscovery` and
  `PatternMatchRouter` instances, decorates its selectors with the pod resolvers, and calls every helper here.
- Retry, fallback, cooldown and alerting (`failure-handling`, [FAILURE-138], [FAILURE-021], [FAILURE-175]). This module only formats the fallback outcome
  messages and truncates the failure detail.
- `calculate_max_parallel_requests` (in `litellm/utils.py`), `get_llm_provider` / `inferred_provider`
  (in `litellm/litellm_core_utils/get_llm_provider_logic.py`), and the per-user OAuth mode check
  `github_copilot_auth_mode` (in `litellm/llms/github_copilot/per_user_auth.py`). This spec describes them
  only as far as their results show through this module.
- Constants (`litellm/constants.py`) and types (`litellm/types/router.py`, `litellm/types/utils.py`).

Inbound callers:
- `litellm/router.py` (all modules `router-*`).
- `litellm/proxy/**`: `proxy_server` (search-tool sync), `model_management_endpoints` (pod lookup),
  `auth_checks`, `policy_validator`, `response_api_endpoints`, `route_llm_request`, `health_check`,
  `health_endpoints`, `credential_hydration`, and the alias resolution in `user_api_key_auth`,
  `common_request_processing`, `litellm_pre_call_utils` and others.

  `is_batch_retrieve_call_type`.
- `litellm/integrations/prometheus.py` uses `PatternMatchRouter`.
- `litellm/litellm_core_utils/prompt_templates/common_utils.py` recognizes `InMemoryFile`.

Outbound dependencies: DNS through `socket.getaddrinfo` and the running event loop's `getaddrinfo`; the
process environment's proxy variables; the Router's `cache` (`DualCache`) through its local-only layer;
the Router's `async_function_with_fallbacks`; `httpx.URL` parsing; `urllib.request` proxy-bypass rules.
Module dependency: `failure-handling` (`handle_error.send_llm_exception_alert`).

- [TARGETS-003] {confirmed} `litellm/router_utils/pattern_match_deployments.py:75-88` Adding a deployment under a pattern whose regex is already registered appends it to that regex's list without re-sorting; adding a new regex rebuilds the dict ordered by descending specificity of the regex string, so lookups later try the most specific pattern first.
- [TARGETS-004] {confirmed} `litellm/router_utils/pattern_match_deployments.py:55-59` Specificity ties keep registration order, because the sort is stable even with `reverse=True` (earlier-registered pattern first among equals).

- [TARGETS-024] {confirmed} `litellm/router_utils/kubernetes_pod_discovery.py:257-293` Checks run in this order, and the first failing check returns the deployment unchanged without any DNS: (1) the deployment is a mapping; (2) its `litellm_params` is a mapping; (3) `litellm_params.kubernetes_pod_discovery` is exactly boolean `true` (a string `"true"` or `1` does not enable it); (4) `api_base` is a string; (5) `api_base` parses as a URL; (6) the scheme is not `https`; (7) the scheme is `http`; (8) the host is not an IP literal.
- [TARGETS-025] {confirmed} `litellm/router_utils/kubernetes_pod_discovery.py:267-269`, `litellm/router_utils/kubernetes_pod_discovery.py:539-549` An `https` deployment with discovery enabled is never rewritten, because an IP would break TLS hostname verification; the first time each host is seen, a warning is logged: `Kubernetes pod discovery is disabled for HTTPS host <host> because substituting an IP breaks TLS hostname verification`, where `<host>` is the URL host without port; for example, `api_base` `https://secure.ns.svc:8443/v1` logs `Kubernetes pod discovery is disabled for HTTPS host secure.ns.svc because substituting an IP breaks TLS hostname verification`.
- [TARGETS-026] {confirmed} `litellm/router_utils/kubernetes_pod_discovery.py:137-138`, `litellm/router_utils/kubernetes_pod_discovery.py:293` The cache key is the URL's `(host, port)`; every deployment pointing at the same service host and port shares one pod set and one round-robin position.
- [TARGETS-027] {confirmed} `litellm/router_utils/kubernetes_pod_discovery.py:289-293`, `litellm/router_utils/kubernetes_pod_discovery.py:267-272` The key is the host and port as parsed by `httpx.URL` (httpx 0.28.1). The host is lowercased. The port is `None` when the URL has no port, an empty port, or port `80` (leading zeros allowed) with the scheme written in lowercase. - Pod selection is rendezvous (highest-random-weight) hashing for sessions and per-service round-robin
  otherwise. The hash (8-byte BLAKE2b over the session id, a NUL byte, and the IP) is load-bearing, because
  it decides which pod a session sticks to across processes and restarts ([TARGETS-040]).
- The pod cache is a copy-on-write mapping guarded by a lock. Refresh ownership is tracked with a
  "refreshing" set and a "timed out" set, so a timed-out lookup keeps ownership until its completion callback runs.
- The batch rewrite streams one row at a time so its peak memory is about one row plus the output. The
  managed-files path runs the rewrite once per target model.
- Wildcard specificity is computed on the escaped regex string at registration, never per lookup. This
  keeps rejected unknown-model requests cheap ([TARGETS-012]).
- Several private aliases (`_pattern_to_regex`, `_get_router_metadata_variable_name`,
  `_is_proxy_admin_request`) are kept for compatibility with older call sites.
