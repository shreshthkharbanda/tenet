# Per-deployment rate limits, I/O-token reservations, PTU shares and access windows (LIMITS)

## Purpose
This module decides whether one concrete deployment (a `litellm_params` + `model_info` block inside a model group) may serve a request, based on limits configured on that deployment. It owns four decisions: (1) per-minute request and total-token ceilings (`rpm`, `tpm`) enforced as a pre-call check, (2) separate per-minute input-token and output-token ceilings (`itpm`, `otpm`) enforced by reserving an estimate before the call and reconciling it to actual usage after, (3) per-team PTU shares (`model_info.ptu_shares`) that restrict who a shared provisioned deployment serves and convert each team's share to a tokens-per-minute ceiling, and (4) reserved time windows (`model_info.access_windows`) that keep a deployment for listed teams during a local wall-clock interval. Outcomes are always one of: admit, reject with a rate-limit error, or drop the deployment from the candidate set.

Terms used throughout:
- Deployment: a mapping with keys `model_name` (the model group), `litellm_params` (including `model`, the provider model string), and `model_info` (including `id`, the deployment id).
- Model group: the public `model_name` a caller asks for.
- Counter: an integer in the router's two-tier cache (in-memory plus optional Redis), keyed per deployment per UTC minute.
- Reservation: the input/output token amounts added to a counter before a call and later corrected to actual usage (reconcile) or removed (refund).
- Sentinels: the four reservation bookkeeping keys this module writes into request metadata.
- Sizing row: the Azure PTU capacity entry (`input_tpm_per_ptu`, `output_to_input_ratio`, `cached_input_ratio`) a deployment's model resolves to.

## Scope and boundaries
Files in scope, all under `litellm/router_utils/`:
- `access_windows.py`: window parsing, validation message, activity test, candidate filter.
- `ptu_shares.py`: share-based candidate filter, team share lookup, name-to-deployment resolution, per-team ceiling, capacity lookup and registration warning.
- `pre_call_checks/model_rate_limit_check.py`: the `ModelRateLimitingCheck` callback (TPM/RPM checks, success/failure accounting, dispatch to the I/O-token logic).
- `pre_call_checks/io_token_rate_limit_check.py`: the I/O-token reservation lifecycle, the per-request context slot, and the rate-limit header builder.

Out of scope and owned elsewhere: where the router calls these filters and checks, and the cooldown that follows a rejection (router-selection, router-calls, router-dispatch, failure-handling: [RSELECT-024], [RCALL-071], [RDISP-216], [FAILURE-021]); router-level TPM/RPM usage counters and model-group usage aggregation (router-dispatch, router-deployments: [RDISP-182], [RDEPLOY-144]); PTU pricing terms and the Azure sizing table (`litellm/litellm_core_utils/ptu_pricing.py`, `litellm/llms/azure/ptu_capacity.py`, outside the surveyed scope); the proxy's team PTU limiter (`litellm/proxy/hooks/parallel_request_limiter_v3.py`); the cache implementation (`litellm/caching/**`).

Inbound: router-setup (registers `ModelRateLimitingCheck` from `optional_pre_call_checks`), router-calls (`_update_kwargs_with_deployment` sets the context slot and refunds stale reservations), router-selection (access-window and PTU-share filters, PTU ceiling), router-dispatch (pre-call check dispatch, admission path), router-deployments (registration-time validation and warnings, remaining-usage headers), and from outside the surveyed scope the proxy (`proxy_server.py` config validation, `ptu_share_guard.py`, `ptu_consumption.py`, `parallel_request_limiter_v3.py`). Outbound: the router's `DualCache` (passed in), `litellm.token_counter`, `litellm.get_model_info`, PTU pricing and capacity helpers, `common_utils` team helpers, `verbose_router_logger`.

- [LIMITS-201] {confirmed} `litellm/router_utils/access_windows.py:29`, `litellm/types/router.py:216-251` The error reported is the first in pydantic's order: windows in list order; within a window, field errors in declared field order `start`, `end`, `timezone`, `team_ids` whatever the key order of the input, then unknown-field errors; and a window's `start != end` rule runs only when all four of its fields are valid and it has no unknown field, so `start == end` together with an unknown key `foo` reports only `0.foo: Extra inputs are not permitted`. ## Implementation notes
- The I/O check reads request kwargs through a context slot rather than an argument because the router's pre-call dispatch passes only the deployment; this is why [LIMITS-083] and [LIMITS-101] matter.
- Reservations are stashed in request metadata (not in a side table) so that the post-call callbacks, which receive only logging kwargs, can find the exact counter key and amount; the sentinel stripping in [LIMITS-082] exists because proxy callers control `metadata` ([LIMITS-112]).
- PTU share and access-window filters are generic over the deployment mapping type and return frozen dataclasses; the router converts their results into `BadRequestError`s ([LIMITS-014], [LIMITS-027]).
- Load-bearing choices stated normatively above: UTC `%H-%M` minute keys ([LIMITS-141]), increment-first atomicity ([LIMITS-170], [LIMITS-171]), the `1`-token floor for failed estimates ([LIMITS-092]), and the default rate-limit category ([LIMITS-062]).
- There is no dead code in scope; the sync variants (`pre_call_check`, `io_token_pre_call_check`, `io_token_reconcile_success`, `io_token_refund_failure`, `log_success_event`, `log_failure_event`) are live for the router's sync call paths and for `refund_stale_reservation_before_retry`.

## Suspected defects
Behavior that looks unintended. The normative sections above state what the code does; each claim here says why it looks wrong and who is affected.

- [LIMITS-197] {confirmed} `litellm/exceptions.py:463-486`, `litellm/router_utils/pre_call_checks/model_rate_limit_check.py:199-212` This module's own TPM, RPM, ITPM and OTPM rejections carry the default category `vendor_rate_limit` ([LIMITS-062]). Looks unintended because the router's other self-imposed limits mark themselves `litellm_rate_limit` ([TARGETS-073], [RDISP-221]), and [LIMITS-193] records no reason. Impact: dashboards, retry logic and clients that branch on the category treat a LiteLLM-imposed limit as a provider limit.
- [LIMITS-198] {inferred} `litellm/router_utils/pre_call_checks/model_rate_limit_check.py:132-140`, `litellm/router_utils/pre_call_checks/model_rate_limit_check.py:366-378` The TPM pre-call check reads a counter keyed by `litellm_params.model`, while success tracking writes one keyed by `hidden_params.litellm_model_name` ([LIMITS-053], [LIMITS-067]). Looks unintended because the limit only works when both are the same key ([LIMITS-192]). Impact: when the two names differ, for example by a provider prefix, usage lands under a key the check never reads and the TPM limit is never enforced.
- [LIMITS-199] {confirmed} `litellm/router_utils/pre_call_checks/io_token_rate_limit_check.py:180-198`, `litellm/router_utils/pre_call_checks/io_token_rate_limit_check.py:237-238`, `litellm/litellm_core_utils/litellm_logging.py:2764-2765` Billable input subtracts `cache_read_input_tokens` from the prompt count even for usage shaped like Anthropic's raw API, whose `input_tokens` already excludes cache reads, so such usage passed to the reconcile functions directly is double-subtracted (`{"input_tokens": 3, "cache_read_input_tokens": 1}` reconciles to `2`, [LIMITS-105]). Looks unintended because cache reads are then subtracted twice ([LIMITS-191]). Impact: latent; no router success event carries that shape, because every one (`acompletion`, `completion`, streaming, `aanthropic_messages` with or without streaming, `aresponses`) delivers a `ModelResponse` whose `prompt_tokens` include cache reads (an Anthropic reply with `input_tokens` 10 and `cache_read_input_tokens` 1000 arrives as `prompt_tokens` 1010 and resolves to the correct billable `10`), and router success events are never reconciled anyway ([LIMITS-190]); only a direct caller passing raw Anthropic usage under-counts ITPM.
- [LIMITS-200] {confirmed} `litellm/router_utils/pre_call_checks/model_rate_limit_check.py:346-348`, `litellm/router_utils/pre_call_checks/model_rate_limit_check.py:412-414`, `litellm/router_utils/pre_call_checks/io_token_rate_limit_check.py:298-311` The success event's reconcile gate looks for the stash only in the callback kwargs' top-level `metadata` and `standard_logging_object.metadata`, and the router's success kwargs never carry it there ([LIMITS-190]), so no successful router call is ever reconciled, while the failure path, which reads all four channels ([LIMITS-102]), does refund. Looks unintended because the module states that the post-call step reconciles ITPM to actual input and OTPM to actual output, the gate's own comment says a missed reconcile leaves the counter elevated until the TTL expires, and the module's tests drive the success event only with hand-built kwargs, never through a router call. Impact: on every I/O-limited deployment each successful call holds its whole reservation for the rest of the minute: OTPM is charged the requested `max_tokens` (or the model default, or `4096`) instead of the tokens produced, so OTPM rejects well below the configured output rate, and ITPM is charged the pre-call estimate instead of the billable input, which over-admits when the estimate is low (an `aresponses` call estimated at `4` input tokens that billed `10`) and under-admits when it is high.
- [LIMITS-205] {confirmed} `litellm/router_utils/pre_call_checks/model_rate_limit_check.py:366-374`, `litellm/router_utils/pre_call_checks/model_rate_limit_check.py:431-435` A deployment's `tpm` limit ignores the router's streaming chat calls and its Anthropic-messages calls, because their success events carry no `litellm_model_name` and TPM tracking skips them ([LIMITS-204]). Looks unintended because the success event receives the deployment's `model_id` and the call's `total_tokens` either way, and the pre-call key is built from `litellm_params.model`, which the success path could use. Impact: tokens from streaming or `/v1/messages` traffic never count toward a deployment's `tpm` limit, so the limit does not bound that traffic at all.
