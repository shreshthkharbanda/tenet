# Routing configuration and model capability contracts (CONTRACTS)

## Purpose
This module is a set of pure, side-effect-free functions and constants that define what a valid routing configuration or model capability is, so that the Router (SDK) and the proxy's config loader and management endpoints all answer these questions the same way. It decides five things no other module decides: (1) how `routing_groups` are parsed and validated and how a priority group rewrites a member deployment's `order`; (2) how an `auto_router/...` pseudo-model string is classified into a strategy-router kind, which settings each kind requires, which other model names it depends on, and which license-metered ("gated") capabilities a complexity-router config claims; (3) the baseline-relative quota gate for edits to heuristic-v1 complexity-router scoring rules (fingerprints, router identities, snapshots, violation messages); (4) which request parameters form an auto-router "baseline request" and how a baseline request is projected; (5) which `reasoning_effort` levels a deployment, and by intersection a model group, accepts.

Terms used throughout:
- Strategy router (auto-router): a deployment whose `litellm_params.model` starts with `auto_router/`; the string after the prefix selects a pre-routing strategy, not a provider model.
- Complexity router: a strategy router whose name after the prefix starts with `complexity_router`; it is configured by a `complexity_router_config` mapping.
- Gated capability: a complexity-router feature whose number of routers is capped by a caller-supplied limit (the proxy derives the limit from its license).
- Violation string: a human-readable reason a configuration is refused; every validator in this module returns one (or `None` when acceptable) instead of raising, except the routing-group functions, which raise `ValueError`.

### Heuristic-v1 tuning quota (`auto_router_tuning_baseline.py`)
The quota limits how many heuristic-v1 complexity routers may carry scoring rules that differ from a recorded baseline. ## Validation rules

1. Per-element construction of `RoutingGroup`, including the priority-group rules ([CONTRACTS-120] to [CONTRACTS-123]); raises pydantic `ValidationError`, or `TypeError` for a non-mapping element or a non-string key ([CONTRACTS-120]). 3. No group named `default` ([CONTRACTS-125]).
4. Unique group names ([CONTRACTS-126]).
5. Valid strategy for each non-priority group ([CONTRACTS-127]).
6. No model in two non-priority groups ([CONTRACTS-128], [CONTRACTS-129]).
7. Unknown member models only warn ([CONTRACTS-130]).

## Implementation notes
Informative.
- Load-bearing choices already stated as normative claims: the fingerprint hash and canonical JSON form ([CONTRACTS-073], [CONTRACTS-074]) must stay byte-stable because fingerprints are persisted in the database and compared across releases; the binary `scoring_mode` exclusion ([CONTRACTS-072]) exists to keep pre-existing hashes valid; the baseline name suffix `_v3` ([CONTRACTS-067]) was bumped because older hashes mixed model selection with scoring rules.
- Each gated capability carries its in-process predicate and its SQL predicate on one record so that the license count in the database and the count in memory answer the same question ([CONTRACTS-051], [CONTRACTS-064] to [CONTRACTS-066]).
- Strategy-router dependency and capability helpers accept `object` and coerce non-mappings to an immutable empty mapping, which is why malformed configs never raise ([CONTRACTS-050], [CONTRACTS-059]).
- The baseline budget check is a lazy running sum, so a huge value is rejected without first serializing or validating it ([CONTRACTS-088], [CONTRACTS-092]).
- Returned mappings are wrapped in read-only views; nested values are not frozen ([CONTRACTS-093], [CONTRACTS-138]).
- The reasoning-effort module's polarity rules (opt-out for `minimal`/`low`/`none`, opt-in for `xhigh`/`max`) mirror the Chat Completions request gates so that what a model group advertises matches what a request to it accepts ([CONTRACTS-113], [CONTRACTS-114]).

## Suspected defects
Behavior that looks unintended. The normative sections above state what the code does; each claim here says why it looks wrong and who is affected. The Router-side reasoning-effort aggregation that contradicts [CONTRACTS-115] is recorded in its owning module as [RDEPLOY-210].

- [CONTRACTS-155] {confirmed} `litellm/router_utils/auto_router_model_naming.py:99-112`, `litellm/router_utils/auto_router_model_naming.py:163` `strategy_router_dependencies` skips complexity tiers written in the object form (a mapping with `model_name`) ([CONTRACTS-049]). Looks unintended because the complexity-router config model accepts that form ([CONTRACTS-147]). Impact: health checks and auto-router permission checks, which enumerate dependencies through this function ([CONTRACTS-012]), do not cover those tier models.
- [CONTRACTS-156] {confirmed} `litellm/router_utils/reasoning_effort_capability.py:177-180` A deployment that declares `reasoning_effort_levels` but sets neither `supports_reasoning` nor any per-level flag resolves to `()` or `None` without reading the declaration ([CONTRACTS-110]). Looks unintended because a declared list otherwise wins whole over the per-level flags ([CONTRACTS-111], [CONTRACTS-151]). Impact: an operator's explicit level list is ignored and the deployment advertises no levels.
- [CONTRACTS-157] {confirmed} `litellm/router_utils/auto_router_model_naming.py:218-221`, `litellm/router_utils/auto_router_model_naming.py:305-307` For a stored complexity config holding both `jev_classifier_config` and `opensource_classifier_config` with `classifier_type` `jev`, the SQL capability predicate claims the custom-prompt capability while the in-process predicate does not ([CONTRACTS-150]). Looks unintended because the two spellings must give the same answer ([DATA-157]). Impact: if such rows exist in the database, license enforcement counts gated routers differently depending on the path.
