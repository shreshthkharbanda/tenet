# Deployment selection pipeline and router settings (RSELECT)

## Purpose
This module decides which concrete deployment of a model group serves a request. It resolves the requested
name (deployment id, `model_group_alias`, routing group, exact `model_name`, team public name, wildcard
pattern, default fallback), narrows the candidates through a fixed sequence of filters (reservations, PTU
shares, access groups, team, web search, health checks, cooldowns, admin pause, callback checks, pre-call
context-window / RPM / region / unsupported-param checks, tags, routing plugins, `order`, weighted-failover
and retry exclusions), runs the pre-routing strategy hook (auto / complexity / adaptive / quality routers and
the claude-code session binding), then hands the survivors to the configured strategy selector. It also owns
the router's runtime-mutable settings (`get_settings`, `update_settings`), the retry / allowed-fails policy
lookups, cached-client lookup, custom-strategy installation, and cache flush / reset.

## Behaviors

Terminology used below. A *deployment* is a dict with `model_name`, `litellm_params` and `model_info`
(`model_info.id` is its id). A *model group* is the set of deployments sharing a `model_name`. A *strategy
marker* is a deployment whose `litellm_params.model` names a strategy router (prefix `auto_router/`); it
registers a pre-routing strategy and is never itself callable. `request_kwargs` is the per-request kwargs
dict; the selection pipeline reads it and also writes bookkeeping into it in place.

### Per-tier params a pre-routing strategy pins onto the request

A pre-routing strategy can return per-tier `litellm_params` (operator overrides for the tier it chose). These

## Validation rules

Selection validates almost nothing about its inputs; it resolves names and filters candidates, and every
failure surfaces as one of the errors in the next section.

Checks inside the pipeline, in order of evaluation for an async request: name resolution errors
([RSELECT-022], [RSELECT-016], [RSELECT-024], [RSELECT-288]) -> team ambiguity ([RSELECT-041]) -> paused single
deployment ([RSELECT-042]) -> callback checks ([RSELECT-047]) -> pre-call errors ([RSELECT-208]-[RSELECT-210])
-> tag routing errors ([RSELECT-049]) -> plugin narrowing ([RSELECT-089]) -> empty set ([RSELECT-054]) ->
selector returning nothing ([RSELECT-068]) -> override pre-call check on the picked deployment ([RSELECT-284]).

## Implementation notes
Informative.
- Selection is split into an async pipeline (`async_get_healthy_deployments`, the only path that runs the
  pre-routing hook, team/web-search filters, optional pre-call callbacks, tag routing and plugin narrowing)
  and a reduced sync pipeline. The async entry point falls back to the sync pipeline for router-level
  strategies without an async-native selector ([RSELECT-060]); that fallback is why configured plugins make
  such routers fail closed ([RSELECT-120]).
- `async_get_available_deployment` and `get_available_deployment` are not `def`s: they are class attributes
  produced by wrapping the `*_unresolved` methods with Kubernetes pod-discovery decorators, and
  `set_custom_routing_strategy` can shadow them per instance with `setattr`.
- Three names are second class attributes bound to an existing method:
  `_is_model_access_group_for_wildcard_route`, `_get_model_from_alias`, `_is_deployment_blocked`; they are
  aliases kept for callers using the old private names.
- The pre-call check avoids deep copies (shallow list copy) and counts tokens at most once per call; the
  off-loop count exists so multi-megabyte prompts do not block the proxy's event loop.
- Metadata bucket choice: proxy-internal keys go to `litellm_metadata` when present so they are not forwarded
  to providers by routes such as `/v1/messages` that pass `metadata` through.
