# Cooldowns, deployment health state, retry policy and fallback bookkeeping (FAILURE)

## Purpose
This module decides what the Router does after a call to one deployment fails. It decides whether
that deployment is put into cooldown, for how long, and where the cooldown entry lives so that every
replica sees it. It keeps the per-minute success/failure counters, the allowed-fails counters and the
health-check state that selection filters on. It resolves how many retries a retry policy grants
for an exception, which fallback model group is tried next, how each fallback hop is recorded so no
attempt repeats, and which response headers (`x-litellm-attempted-retries`,
`x-litellm-attempted-fallbacks`, `x-litellm-fallback-errors`, complexity- and quality-router headers)
report it. It also builds the "no deployments available" error and the optional alert for failed
calls.

Terms used throughout:
- *Deployment*: one concrete `litellm_params` entry, identified by its `model_info.id` (the "model id").
- *Model group*: the public `model_name` that several deployments share.
- *Cooldown*: a time-boxed exclusion of a deployment from selection, stored under
  `deployment:<model_id>:cooldown`.
- *Router cache*: the Router's shared two-tier cache (in-memory plus optional Redis).
- *Metadata bucket*: the per-request dict named `metadata` or `litellm_metadata` that the Router writes
  bookkeeping into in place.
- *Single-deployment model group*: defined exactly in [FAILURE-034].

## Behaviors

### Cooldown store (`CooldownCache`)
- [FAILURE-001] {confirmed} `litellm/router_utils/cooldown_cache.py:133-136`, `litellm/router_utils/cooldown_cache.py:217` The cooldown entry for a deployment is stored under the key `deployment:<model_id>:cooldown`, with no namespace prefix added by this module. The id string is inserted as is: for example, the deployment with id `dep-a` uses `deployment:dep-a:cooldown`. `get_min_cooldown` builds the same key format inline.
- [FAILURE-002] {confirmed} `litellm/router_utils/cooldown_cache.py:27-31`, `litellm/router_utils/cooldown_cache.py:78-93` A cooldown entry is a dict with four fields. `exception_received` is the masked string form of the exception ([FAILURE-003]). `status_code` is the string form of the status passed in. `timestamp` is wall-clock epoch seconds (float) at write time. `cooldown_time` is the cooldown length in seconds.
- [FAILURE-003] {confirmed} `litellm/router_utils/cooldown_cache.py:55-61`, `litellm/litellm_core_utils/sensitive_data_masker.py:57-72` An exception string of 50 characters or fewer is stored unchanged. A longer string keeps its first 50 characters and replaces every remaining character with `*`, so its length is preserved.
- [FAILURE-004] {confirmed} `litellm/router_utils/cooldown_cache.py:87` A `None` exception is stored as the string `None`. Other exception types are stored as their string form, with no class name prefix added.
- [FAILURE-005] {confirmed} `litellm/router_utils/cooldown_cache.py:105-120` When `add_deployment_to_cooldown` is called with `cooldown_time=None`, it uses the `default_cooldown_time` given at construction. The Router passes its own `cooldown_time` there (`litellm/router.py:1421-1422`). An explicit `0` is kept as `0` and is not replaced by the default.
- [FAILURE-006] {confirmed} `litellm/router_utils/cooldown_cache.py:122-128`, `litellm/caching/redis_cache.py:867-892`, `litellm/caching/base_cache.py:26-33` The entry is written with a TTL equal to the cooldown seconds. The write goes to the cooldown store's in-memory tier and, when a Redis client is attached, to Redis. It runs under the service target `router_cooldowns`. Redis expiries are whole seconds, because the TTL is truncated with `int()`. A `1.7`-second cooldown therefore leaves Redis after 1 second while the entry itself still records `1.7` ([FAILURE-012]). A cooldown shorter than 1 second becomes a Redis `SET` with `EX 0`, which Redis rejects. That failure is swallowed ([FAILURE-203]), so the cooldown exists only in this process's memory and sibling replicas never see it, although `set_cooldown_deployments` still returns `True`.
- [FAILURE-007] {confirmed} `litellm/router_utils/cooldown_cache.py:94-96`, `litellm/router_utils/cooldown_cache.py:129-131` If building or writing the entry raises, the error is logged at ERROR level with `CooldownCache::add_deployment_to_cooldown - Exception occurred - %s` (or the `_common_add_cooldown_logic` variant) and then re-raised to the caller.
- [FAILURE-008] {inferred} `litellm/router_utils/cooldown_cache.py:50-54`, `litellm/router_utils/cooldown_cache.py:63-76`, `litellm/caching/dual_cache.py:119-136` Cooldown entries live in a dedicated two-tier store with its own in-memory cache, separate from the router cache. Unrelated router-cache traffic therefore cannot evict a live cooldown. Each access to `cooldown_store` attaches the router cache's current Redis client, but the attach is a no-op once a client is attached. As a result, a Router whose Redis is wired after construction still publishes cooldowns. If the router's Redis client is later replaced, the cooldown store keeps the first one (the inference rests on the cache's attach semantics, which this module does not own).
- [FAILURE-009] {inferred} `litellm/router_utils/cooldown_cache.py:42-54`, `litellm/constants.py:152` A cooldown key that is missing from the in-memory tier is re-read from Redis at most once per `redis_read_interval_seconds` per key. The default comes from env `DEFAULT_COOLDOWN_REDIS_READ_INTERVAL_SECONDS`, which defaults to `1.0` seconds. A cooldown written by one replica therefore becomes visible to sibling replicas within about that interval (the throttle itself lives in the two-tier cache; the visibility is pinned by tests).
- [FAILURE-010] {inferred} `litellm/caching/dual_cache.py:103-105` A Redis read interval of `0` (or any falsy value) does not disable throttling. The store falls back to the process-global `litellm.default_redis_batch_cache_expiry` and, if that is unset, to `10` seconds.
- [FAILURE-011] {confirmed} `litellm/router_utils/cooldown_cache.py:193-211` `get_active_cooldowns` batch-reads the cooldown keys of the given model ids. It returns `(model_id, entry)` pairs for every result that is a non-empty dict and still active ([FAILURE-012]), in the order of the input ids. Missing ids are left out.
- [FAILURE-012] {confirmed} `litellm/router_utils/cooldown_cache.py:138-153` An entry is active while `timestamp + cooldown_time - now > 0`, using wall-clock seconds. When `remaining <= 0`, the entry is deleted from the cooldown store's in-memory tier and left out of the result. Expired data is filtered on every read, whatever TTL the store holds.
- [FAILURE-013] {confirmed} `litellm/router_utils/cooldown_cache.py:155-159` If an active entry's in-memory expiry is more than `remaining + 5` seconds in the future, the entry is rewritten in memory with TTL `min(remaining, 60)` seconds. This happens, for example, after a Redis backfill that applied the cache's 600-second default. The 60-second cap makes the store re-check Redis at least once a minute while the cooldown lasts.
- [FAILURE-014] {confirmed} `litellm/router_utils/cooldown_cache.py:184-189`, `litellm/router_utils/cooldown_cache.py:204-209` Batch results that are `None`, empty or not a dict are ignored, with no error and no log.
- [FAILURE-015] {inferred} `litellm/router_utils/cooldown_cache.py:200`, `litellm/caching/dual_cache.py:218-260` On the sync read path, if Redis raises an error other than an open circuit breaker, the two-tier cache logs it and returns `None`. This module treats that as an empty result, so no deployment is reported as cooling down, including entries that were in memory. With the circuit breaker open, only the in-memory entries are returned.
- [FAILURE-016] {confirmed} `litellm/router_utils/cooldown_cache.py:162-191` `async_get_active_cooldowns` does the same batch read asynchronously and passes the raw results to `active_cooldowns_from_results`. That method returns `[]` when the results are `None` or all `None`, and otherwise applies [FAILURE-012] to [FAILURE-014] per id.
- [FAILURE-017] {confirmed} `litellm/router_utils/cooldown_cache.py:213-231` `get_min_cooldown` returns the smallest stored `cooldown_time` among the ids' entries that are present. It does not check expiry or correct TTLs. The value is the configured cooldown length, not the time remaining. It returns `default_cooldown_time` when no entry is found or when the smallest value is `0`.
- [FAILURE-018] {confirmed} `litellm/router_utils/cooldown_cache.py:38`, `litellm/router_utils/cooldown_cache.py:123`, `litellm/router_utils/cooldown_cache.py:168`, `litellm/router_utils/cooldown_cache.py:199`, `litellm/router_utils/cooldown_cache.py:220` Every cooldown store write and batch read, sync and async, runs under service target `router_cooldowns`, so Redis service spans read for example `redis.set router_cooldowns` and `redis.mget router_cooldowns`. The target is restored afterwards.
- [FAILURE-019] {inferred} `litellm/router_utils/cooldown_cache.py:124-128`, `litellm/caching/in_memory_cache.py:162-192` When a deployment that is already cooling down is cooled again, its entry is replaced: new timestamp, status and length. The in-memory tier keeps the existing unexpired TTL, because the in-memory cache does not override a live TTL. Without Redis, a longer second cooldown is therefore cut short when the first TTL expires. With Redis, the Redis copy carries the new TTL and is re-read once the memory copy expires ([FAILURE-009]).
- [FAILURE-020] {gap} `litellm/router_utils/cooldown_cache.py:150-151` What happens when a stored cooldown value is a dict that lacks `timestamp` or `cooldown_time`, for example one written by another version? Building the entry does not validate it, and the arithmetic would raise a missing-key error out of the read. No test covers this case.

## Implementation notes
- Dead or redundant code: the second `deployment is None` check in the gate list
  (`cooldown_handlers.py:372-374`) is unreachable after gate (1); the trailing `return False` after the
  rate-based and threshold branches of the decision is unreachable; the `PrometheusLogger is None`
  check in the logger lookup never triggers; `run_non_standard_fallback_format` is an empty stub
  ([FAILURE-136]); and the tuple-type check on cooldown read results is always true.
- Cooldown keys are memoized per model id (an LRU cache of 1024 entries). This affects only speed.
- The cooldown store is deliberately separate from the router cache for two reasons: a much shorter
  Redis re-read interval than the router cache's default batch interval (10 s), and isolation from
  in-memory eviction by unrelated keys. This is load-bearing for cross-replica visibility, so it is
  stated normatively in [FAILURE-008] and [FAILURE-009].
- Fallback identities use SHA-256 over sorted-key JSON rather than storing the payload, so a large
  `messages` override is not held twice. Only the equality semantics in [FAILURE-109] are observable.
- The per-type allowed-fails matching order lists `ContentPolicyViolationError` before
  `BadRequestError` because it is a subclass. The retry-policy lookup walks the class hierarchy
  instead. Both give subclass-first precedence.
- `RoutingReadBatch` and `RoutingPrefetch` exist to merge the cooldown MGET and the usage-counter MGET
  into one Redis round trip, and the prefetch can ride the admission-time Redis batch. Neither changes
  routing outcomes. A failed batched read degrades exactly as two failed reads would.

- [FAILURE-208] {confirmed} `litellm/router_utils/cooldown_handlers.py:450-453`, `litellm/router_utils/cooldown_handlers.py:734-748` A router `allowed_fails` equal to the current `litellm.allowed_fails` (default `3`) counts as not set, so the rate-based default rules decide instead of the allowed-fails counter ([FAILURE-042], [CFG-051]). Looks unintended because an explicit setting is ignored only when it happens to equal the global default. Impact: `Router(allowed_fails=3)` gets the failure-rate rules of [CFG-118] rather than the counter of [FAILURE-047].
- [FAILURE-209] {confirmed} `litellm/router_utils/cooldown_handlers.py:254-258` Cooldown is suppressed whenever the exception's string form contains `APIConnectionError` ([FAILURE-031]). Looks unintended because the test is a substring of the message, not the exception type, so a wrapped upstream message that mentions the name also suppresses cooldown ([FAILURE-202]). Impact: any error whose text mentions `APIConnectionError` never cools its deployment by status, whatever its real status code.
- [FAILURE-210] {confirmed} `litellm/router_utils/cooldown_cache.py:55-61`, `litellm/router_utils/handle_error.py:91-93` Cooldown entries mask exception text by length only, so the first 50 characters, including any credential fragment there, are stored, listed in the debug-info cooldown list and logged at INFO ([FAILURE-003], [FAILURE-204]). Looks unintended because the alert path redacts secrets from the same text ([FAILURE-176]). Impact: a provider error that echoes a key early in its message puts that fragment in Redis and in logs.
- [FAILURE-211] {inferred} `litellm/router_utils/cooldown_handlers.py:556-563` `set_cooldown_deployments` schedules its event callback on the running event loop, so a call from synchronous code with no running loop raises `RuntimeError` after the cooldown entry was written ([FAILURE-053]). - [FAILURE-212] {confirmed} `litellm/router_utils/add_retry_fallback_headers.py:250-260`, `litellm/router_utils/add_retry_fallback_headers.py:345-356` `x-litellm-fallback-errors` carries the full message of every failed hop with no size limit ([FAILURE-206]). - [FAILURE-216] {confirmed} `litellm/router_utils/fallback_event_handlers.py:870-876` On a success reached through a nested walk, each enclosing walk overwrites `x-litellm-attempted-fallbacks` with its own smaller depth ([FAILURE-213]).
